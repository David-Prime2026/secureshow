SecureShow Codebase Review & Required Actions

FromPRIME Time Systems ToCorpsoft Solutions — Development Team DateOctober 5, 2026 ReCode audit of secureshow-backend and secureshow-frontend repositories (development branches)
Summary: PRIME has completed an independent audit of both SecureShow repositories. The core permission chain and five-point unlock validation are fully implemented, and the overall engineering quality is strong. This report addresses three required corrections, two vendor alignment items, and the remaining work for production readiness.

1. Overall assessment

The development branch of both repositories reflects substantial, well-structured work: 133,749 lines added across 1,475 backend files, 239 backend test files, 126 frontend spec files. All 11 steps of the SecureShow permission dependency chain are implemented and tested. The five-point unlock validation (credential, time window, device binding, geofence, facial match) is enforced server-side.

The gateway abstraction pattern used for locks (LockGateway) and cameras (LockCameraGateway) is well-designed, with contracts and fake implementations for testing. The frontend unlock flow is particularly thorough, handling 15 distinct states with accessibility annotations, attempt limiting, session management, and visibility-aware polling.

2. Required corrections

The following items must be addressed before production deployment. Items marked CRITICAL are blockers.

Critical — Database engine
MySQL must be replaced with PostgreSQL.

Both the PRIME technical specification and the Corpsoft Product Technical Roadmap specify PostgreSQL (AWS RDS). The codebase uses MySQL 8.0 as its default database connection. This substitution was not authorized or discussed with PRIME. A pgsql configuration block already exists in the Laravel config. The migration to PostgreSQL should be completed before any production data is written. Delaying this increases the cost and risk of switching.

Required action: Switch DB_CONNECTION to pgsql, verify all migrations against PostgreSQL dialect, update Docker Compose to use PostgreSQL, and confirm functionality in staging. Provide a timeline by October 10.

Critical — CORS configuration
CORS allowed origins must be restricted.

The current configuration sets allowed_origins: ['*'], which permits any domain to make authenticated requests to the API. This is acceptable for local development but is a security vulnerability in any deployed environment.

Required action: Restrict allowed_origins to the actual frontend domain(s) in all non-local environment configurations. This should be completed before the next staging deployment.

Critical — Branch management
The main branch does not reflect the application state.

The main branch contains only the initial Laravel scaffold commit. The development branch is 332 commits ahead with 100% of the application code. If a deployment targets main, it deploys a skeleton application. Both repositories exhibit this pattern.

Required action: Merge development into main and establish branch protection rules. Provide confirmation when complete.

3. Contract template content

Requires clarification
RPM Financial vehicle financing agreement templates in the codebase.

The contract blade templates (resources/views/contracts/components/page1-30.blade.php) contain a 30-page vehicle financing agreement for "RPM Financial." This appears to be content from a different Corpsoft project. SecureShow requires a property showing liability agreement, not a vehicle financing contract.

Required action: Confirm whether this content is placeholder scaffolding or was included in error. If placeholder, provide a timeline for replacing it with the SecureShow-specific liability agreement.

The codebase shows both fully implemented with tests, along with the complete permission chain, PM dashboard, PM onboarding, and 28+ notification classes.

7. What is working well

PRIME acknowledges the following as strong engineering decisions:

  • Gateway abstraction pattern for locks and cameras — enables vendor swaps without application changes
  • Server-side enforcement of all five unlock preconditions — security controls cannot be bypassed by client manipulation
  • Comprehensive rate limiting with per-endpoint buckets tuned to each route's abuse profile
  • KYC data encryption at rest with separate key streams
  • Device fingerprint binding with rebind requiring OTP verification
  • Architecture enforcement via deptrac preventing accidental layer violations
  • Fake gateway implementations enabling thorough testing without external service dependencies
  • Frontend unlock flow with 15-state machine, accessibility annotations, attempt persistence for reload recovery, and visibility-aware polling
  • 239 backend test files and 126 frontend specs demonstrating real test investment
